What a Unix timestamp actually is

It is the number of seconds since 00:00:00 UTC on 1 January 1970, excluding leap seconds. It is a count, not a date format — which is why the same instant has one integer timestamp worldwide but many local time representations.

Seconds or milliseconds?

The most common bug. JavaScript's Date.now() returns milliseconds; Unix timestamps and most backend APIs use seconds. Mixing them produces dates in 1970 or the year 55,000. This tool detects which you meant by magnitude: values below 10¹¹ are treated as seconds, above as milliseconds.

The 2038 problem

Systems storing a timestamp in a signed 32-bit integer overflow on 19 January 2038 at 03:14:07 UTC, when the counter exceeds 2,147,483,647. The result wraps to a date in 1901. Modern 64-bit systems are unaffected, but embedded devices, legacy file formats and old database column types still carry the risk.

Timestamps ignore leap seconds

Unix time pretends every day has exactly 86,400 seconds. Real UTC occasionally inserts a leap second to stay aligned with Earth's rotation, and Unix time simply repeats or skips as needed. For most applications this is invisible, but high-precision logging and astronomy need a time scale that accounts for it.

Why store timestamps at all?

Integers sort chronologically, compare cheaply, need no timezone parsing and take little space. The trade-off is human unreadability, which is exactly why conversion tools like this exist. Store in UTC, convert only for display.
